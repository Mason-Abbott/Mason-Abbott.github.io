Edge API Security Policy Engine

Java 21 • Fail-Closed Pipeline • Per-IP Token Bucket • BOLA & Schema Validation

Fail-closed request policy evaluator enforcing per-IP rate limiting, token authentication and object-ownership checks, and positive-allowlist payload validation before traffic reaches downstream services.

1. Problem Solved & What I Built

Transport reliability and link-layer checks do not stop application-layer abuse—such as burst floods saturating edge capacity, unauthorized cross-user access to resources, or malformed payloads reaching backend handlers. This policy engine evaluates requests at the edge boundary and rejects invalid, ambiguous, or unauthorized traffic by default.

What I implemented: EdgePolicy.java (allowRateLimit, checkAuthAndBola, validateSchema, and evaluate).

Provided harness: Main.java (trace parser, token-bucket setup, and output formatting), the Makefile (javac -Xlint:all -Werror build and trace test target), and the five trace fixtures in test_tr/.

2. Architecture, Tradeoffs & Invariants

evaluate runs requests sequentially through a short-circuiting three-stage pipeline so invalid traffic exits before touching later checks:

  1. Per-IP Token-Bucket Rate Limiting (429 RATE_LIMIT): Each client IP has an independent bucket initialized at full capacity, refilling by elapsedSec * refillPerSec up to capacity, and consuming 1.0 token on pass. Evaluating rate limiting first with per-IP buckets prevents one noisy IP from starving others and avoids spending auth/parsing work on floods, at the tradeoff that a flood request can consume a token even if it would later fail validation.
  2. Fail-Closed Auth & BOLA Authorization (401 UNAUTHENTICATED, 403 UNKNOWN_ROUTE, 403 BOLA_FORBIDDEN): Missing, -, or unknown tokens fail closed with 401 UNAUTHENTICATED. Paths must begin with / and match a valid users or orders route with a non-empty owner segment, or fail with 403 UNKNOWN_ROUTE. Matching owners or admin callers pass; mismatched non-admin owners fail with 403 BOLA_FORBIDDEN.
  3. Positive-Allowlist Schema Validation (400 SCHEMA_INVALID): Rather than denylisting known bad strings, GET requires an empty or - body, and POST /orders/<owner> requires semicolon-delimited key=value fields with no duplicate or unknown keys and strictly item (1–32 chars in [A-Za-z0-9_-]) and amount (integer from 1 to 10000). Positive allowlisting avoids blind spots caused by incomplete denylists.

3. Verification & Edge Cases

Built with javac -Xlint:all -Werror (zero compiler warnings) and verified across all five scenarios in test_tr/ (clean.trace, ratelimit.trace, bola.trace, schema.trace, and mixed.trace).

Boundary & failure cases checked: Verified strict stage ordering so a client with fewer than 1.0 token receives 429 RATE_LIMIT even on a valid route and payload; checked that duplicate or extra keys in POST /orders/<owner> are rejected rather than overwritten; confirmed admin callers pass ownership checks while cross-owner non-admin requests fail with 403 BOLA_FORBIDDEN; and verified denied responses omit authenticated user attribution (-) consistently.
