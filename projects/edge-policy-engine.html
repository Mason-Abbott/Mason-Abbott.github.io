Edge API Security Policy Engine

Java 21 • Fail-Closed Pipeline • Per-IP Token Bucket • BOLA & Schema Validation

Fail-closed request policy evaluator enforcing per-IP rate limiting, token authentication and object-ownership checks, and positive-allowlist payload validation before traffic reaches downstream services.

View Repository on GitHub Back to Projects

1. Problem Solved & What I Built

Network-level packet delivery and link-layer error checks do not stop application-layer abuse such as burst flooding, unauthorized object access, or malformed payloads. This policy engine evaluates requests at the edge and rejects invalid or unauthorized traffic by default.

What I built: I implemented EdgePolicy.java (allowRateLimit, checkAuthAndBola, validateSchema, and evaluate). Provided scaffold: Main.java (trace parser, token/bucket setup, and result formatter), Makefile (javac -Xlint:all -Werror build and make test), and the five traces in test_tr/ were provided by the course.

2. Architecture, Tradeoffs & Invariants

Requests run sequentially through a short-circuiting three-stage pipeline so rejected traffic stops immediately:

  1. Per-IP Token-Bucket Rate Limiting (429 RATE_LIMIT): Each client IP gets an independent token bucket starting full, refilling by elapsedSec * refillPerSec up to capacity, and spending 1.0 token on pass. Per-IP buckets isolate clients so one noisy IP cannot starve others.
  2. Fail-Closed Auth & BOLA Authorization (401 UNAUTHENTICATED, 403 UNKNOWN_ROUTE, 403 BOLA_FORBIDDEN): Missing, -, or unknown tokens return 401 UNAUTHENTICATED. Paths must start with / and match valid users or orders routes with a non-empty owner segment, or return 403 UNKNOWN_ROUTE. Matching owners or admin callers pass; mismatched non-admin owners fail with 403 BOLA_FORBIDDEN.
  3. Positive-Allowlist Schema Validation (400 SCHEMA_INVALID): Instead of denylist matching, GET requires an empty or - body, and POST /orders/<owner> requires semicolon-separated key=value fields with no duplicate or extra keys and strictly item (1–32 chars in [A-Za-z0-9_-]) and amount (integer from 1 to 10000).

3. Verification & Edge Cases

Compiled cleanly with javac -Xlint:all -Werror and verified across all five traces in test_tr/ (clean.trace, ratelimit.trace, bola.trace, schema.trace, and mixed.trace) via make test.

Key edge cases verified include strict stage precedence (a client below 1.0 token receives 429 RATE_LIMIT even on a valid route/body), rejecting duplicate or unknown fields in POST /orders/<owner>, returning "-" as the user ID on denied decisions, and allowing admin access while blocking cross-owner non-admin requests.
